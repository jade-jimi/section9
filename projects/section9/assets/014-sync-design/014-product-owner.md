# REQ-20260902-014-62x6 다중 사용자 요청 동기화 — product-owner 판정

작성: product-owner · 2026-09-02 · 근거는 bin/s9·docs·vault 를 직접 읽은 것만. 미확인은 표시.

## 0. 결론 먼저

1. **사용자의 "자기 요청은 자기 머신에서" 우선 판단은 맞습니다. 다만 기준어가 틀렸습니다** — "자기 머신"이 아니라 **"자기(담당자)"** 여야 합니다. 머신을 기준으로 잡으면 한 사람이 두 대를 쓰는 순간(시나리오 C) 깨지고, 담당자를 바꾸는 순간(시나리오 A) 막힙니다. 축 1(실행 귀속)과 축 2(생성자/담당자)는 별개가 아니라 **한 기능의 앞뒤**입니다: 담당자 필드가 없으니 귀속을 machine 으로 흉내 내고 있는 것입니다(bin/s9:7247).
2. 중복 실행의 실제 구멍은 워처가 아니라 **리드 세션에 훅이 주입하는 목록**입니다. 워처는 이미 machine 가드가 있지만(7247), 매 프롬프트마다 주입되는 `s9 reopened`·`stalled`·`approvals` 는 user 도 machine 도 보지 않습니다(11061~11067 `cmd_reopened` → `reopened_requests()` 무필터; `cmd_stalled` 10979~ 무필터; `cmd_approvals` 11137~ 는 user 를 출력만). pull 로 남의 반려 REQ 가 오면 내 리드가 "우선 이어서 작업하라"는 지시를 받습니다(bin/s9-audit-prompt:726~730).
3. 축 3(동기화 방식)은 **새 설계를 하지 않습니다.** 이미 DOC-20260826-002 가 확정했고(이벤트 즉시 commit·pull --rebase·push, 단일 main, 문서 1파일), 남은 것은 그 문서의 **결론 D(쓰지 않는 사람도 pull)** 와 **결론 E(실패 표면화)** 가 미구현이라는 사실입니다. 브랜치 분할·디렉토리 분할은 non-goal 로 못 박습니다.
4. 축 4(observer)는 이미 `viewer` role 이 있으니(bin/s9:13147) 새 계정 타입이 아니라 **쓰기 거부 한 곳**만 있으면 됩니다. 우선순위는 셋째입니다 — 지금 등록 사용자 중 실팀원이 0명이라(users/: nicehugepark·user1·user2·e7test) 관찰자보다 작업자 둘이 먼저 안전해야 합니다.

사용자 판단 검증: "자기 요청이 자기 머신에서" 를 **1순위로 둔 것은 옳습니다** — 위 표에서 임팩트·확신도가 가장 높고 비용이 가장 낮습니다. 틀린 부분은 낱말 하나입니다. 제가 보기엔 "자기 머신"은 수단이고 뿌리는 "담당자"입니다. 근거 셋: ① 사용자 자신이 같은 문단에서 "그러면 남에게 할당할 수 없다"는 모순을 이미 발견했습니다 — 머신 기준의 필연적 결과입니다. ② 현행 machine 가드(7247)는 **생성 머신**을 보므로 노트북에서 만든 요청을 데스크톱이 이어받지 못합니다 — 같은 사람인데도. ③ 담당자를 기준으로 하면 "담당자 = 나 AND 이 머신이 내가 지금 쓰는 머신" 이라는 한 판정이 세 상황(남의 것·내 것·내 다른 머신)을 전부 가릅니다.

## 3. 각 축의 최소 완성 상태 (AC)

**축 1+2 · 담당자와 귀속** — "팀이 함께 쓸 수 있다" 의 문턱
- AC1. request frontmatter 에 `assignee`(담당자, 기본값 = 생성 시 user)와 `origin`(생성 경로: `human` | `agent:<actor>` | `agent:<actor> via <REQ-id>`)이 기록된다. 기존 문서는 `assignee` 부재 시 `user` 로 읽는다(마이그레이션 0).
- AC2. `s9 assign <id> <user> [--note]` 로 담당자를 바꾸고 History 에 남는다. 대시보드 카드에서도 같은 함수로 바꾼다.
- AC3. **한 판정 함수** `mine(meta)` = (assignee == 현재 user) — 이것을 `_spawn_worker`(7247 machine 검사 대체), `reopened_requests`, `stalled_requests`, `approvals`, `next_pickup` 다섯 곳이 공유한다. 옆문 없이 한 곳.
- AC4. 남의 반려 REQ 가 pull 돼 와도 내 리드 세션 훅 주입과 워처가 그것을 집지 않는다 — 회귀 시험: 격리 S9_ROOT 에 assignee=B 인 반려 문서를 두고 A 로 `s9 reopened` 실행 시 0건.
- AC5. 같은 사람의 두 머신: 다른 머신 바인딩이 `active_reqs` 에 그 REQ 를 갖고 `claim_at` 이 N분(제안 10분) 이내면 내 머신은 "다른 자리에서 진행 중"으로 표시하고 집지 않는다. **미확인**: 바인딩 stream 신선도 대신 무엇을 생존 신호로 쓸지는 architect 몫.
- AC6. 에이전트가 파생 요청을 만들면 `user` 는 원 요청의 user, `origin` 은 `agent:… via <원 REQ>`, `assignee` 는 원 요청의 assignee 를 상속한다.

**축 3 · 동기화** — 새 설계 없음, DOC-20260826-002 의 미구현분
- AC7. 쓰지 않는 세션도 최신을 본다: SessionStart 1회 + serve 30초 루프에서 활동 중 60초·유휴 5분 pull --ff-only + `s9 digest` 120초 TTL. **체감 최악 60초** (DOC-026-002 확정 수치).
- AC8. pull/push 연속 실패가 1회 이상이면 `s9 digest` 첫 줄·대시보드·SessionStart 컨텍스트에 사유와 다음 행동(`s9 sync`)이 뜬다. 자동 충돌 해결은 계속 금지.
- AC9. 인스턴스 통합 시험: 두 클론(A·B) + bare origin 으로 A 가 assign→B 가 60초 내 보고, B 만 워커를 띄운다.

**축 4 · observer**
- AC10. 시스템 role `viewer` 는 `s9 new request/knowledge`·`status`·`note`·`assign`·대시보드 POST 전부에서 "관찰 계정은 쓰지 못합니다" 로 거부된다 — 게이트는 쓰기 진입점 한 곳(`resolve_user` 직후).
- AC11. 조회(`ls/search/show/digest`, 대시보드 GET)는 현행 `doc_visible` 그대로. 인증은 non-goal(REQ-017 이 명시한 한계 승계).

## 4. 시나리오 — 무엇을 보고 무엇을 누르나

**A. 할당**: A 가 노트북에서 요청을 낸다(`s9 new request`, assignee=A). 카드의 담당자 칩을 눌러 B 를 고른다(`s9 assign REQ B`). B 의 데스크톱은 ≤60초 후 pull 로 받고, B 의 리드 훅이 "내 담당 미착수 1건"을 주입한다. B 가 반려하면 **B 머신의** 워처만 무인 워커를 띄운다. A 의 화면에는 같은 카드가 "담당 B · 진행 중 (B 의 자리)" 로 보이고 A 의 세션은 손대지 않는다.
**B. 관찰자**: C(viewer)가 대시보드를 연다. me 셀렉터에 C 만 보이고, Board·Graph·검색은 되지만 카드 드래그·승인·반려·채팅 전송 단추가 없다. CLI 에서 `s9 new` 를 치면 한 줄 거부. C 는 프로젝트 셀렉터로 프로젝트별 상태만 본다.
**C. 두 대**: A 가 데스크톱에서 in-progress 로 일하다 노트북을 연다. 노트북의 `s9 digest` 는 그 REQ 를 "데스크톱 세션 3ef7 이 12분 전 클레임" 으로 보여 주고 `s9 next` 후보에서 뺀다. 데스크톱 세션이 끝나면(binding ended, pull 됨) 노트북이 이어받을 수 있다.
**D. 파생**: A 의 요청을 처리하던 에이전트가 `s9 new request --parent REQ-A` 로 파생을 만든다. 카드에 "생성: designer (REQ-A 처리 중) · 담당: A" 가 붙는다. B 의 머신은 이 파생을 집지 않는다.
**E. 동기화 실패**: B 의 push 가 충돌로 실패한다. B 의 digest 첫 줄과 대시보드 상단에 "동기화 멈춤 — `s9 sync` 로 확인" 이 뜬다. A 의 화면에는 B 의 변경이 오지 않는 대신 최신 pull 시각이 보인다.

## 5. 기존 결정과의 충돌 확인

- DOC-20260826-002(문서 이벤트 동기화, DOC-024-002 대체): 단일 main·이벤트 즉시·허브 없음 확정 → 사용자의 브랜치/디렉토리 후보는 이 결정과 **충돌**. 권고: 확정 유지. 브랜치 분할은 "거의 실시간·충돌 없음" 목표에 역행(merge 지점이 곧 충돌 지점)하고, 디렉토리 분할은 문서 1파일 원칙으로 이미 충돌 면적이 최소라 얻는 것이 없음.
- REQ-20260828-019: pull/push 는 사람이 고른 remote 모드에서만 → 유지. 축 3 의 주기 pull 도 remote 모드 한정.
- REQ-20260825-006/031: uid 접미로 다머신 발번 충돌 해결 → 축 3 에서 재론 불요.
- REQ-20260824-017: me 자기신고, 인증은 후속 → observer 도 가드레일 수준. 인증 도입은 이 REQ 의 non-goal.

- QST-20260827-027: worktree 는 동기화에 무관 → 후보에서 제외.
- DOC-20260827-006: 권한·비밀은 리포에 싣지 않음 → 바인딩·담당자 정보는 능력을 열지 않으므로 track 가능.

## 6. 파생 REQ 후보 (선후 순)

1. **담당자·생성경로 필드** — goal: request 에 assignee/origin 이 기록·변경되고 구문서는 user 로 읽힌다 · S · 선행 없음
2. **귀속 게이트 단일화** — goal: 남의 담당 REQ 는 훅 주입·워처·next 어디서도 내 머신이 집지 않는다(회귀 시험 포함) · M · 1 뒤
3. **두 머신 클레임 인식** — goal: 같은 사용자의 타 머신 진행 중 REQ 를 표시하고 집지 않는다 · M · 2 뒤
4. **읽기 pull 3지점** — goal: 쓰지 않는 세션도 60초 내 최신을 본다 · M · 독립
5. **동기화 실패 표면화** — goal: 연속 실패가 digest·대시보드에 다음 행동과 함께 뜬다 · S · 4 와 병행
6. **관찰 계정 쓰기 거부** — goal: viewer 는 모든 쓰기 진입점에서 거부되고 조회는 그대로다 · S · 1 뒤(assign 도 막아야 하므로)
7. **두 클론 통합 시험** — goal: A·B 클론 + bare origin 으로 시나리오 A·C·E 가 자동 재현된다 · M · 2·4 뒤

## 8. 다른 역할에게 넘길 질문
- architect: AC5 의 "다른 머신 세션 생존" 신호 — `claim_at` 시각 기반 리스로 충분한가, 바인딩에 heartbeat 를 싣고 push 할 것인가(push 빈도 = 커밋 수).
- backend: `reopened_requests`·`stalled_requests` 는 카탈로그 기반인데 assignee 를 카탈로그에 실으면 index rebuild 비용이 얼마나 느나.
- security: `s9 assign` 을 누가 할 수 있나 — 생성자·현 담당자·프로젝트 maintainer 이상? 시스템 viewer 가 `--user` 플래그로 위장하는 경로.
- designer/ux-writer: 카드의 담당자 칩·"다른 자리에서 진행 중" 표시·관찰 계정의 단추 부재를 어떻게 보이나.
