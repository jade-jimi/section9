## ① 현황 진단 (확인한 사실만)

**동기화 경로** — `sync_run` bin/s9:8506-8590. 호출 지점 11곳(new 1535 · 전이 1855 · link 8786 · set 8826 · assets 9924 · note 12245 · archive 12791 · restore 12879 · purge 12908 · rm 12943). 한 이벤트 = `add → commit --only <스테이징된 데이터 파일> → pull --rebase --autostash(8s) → push(8s)` 를 **호출 프로세스 안에서 동기로** 수행. 락 `state/.sync.lock`(30초 stale), 백오프 `state/.sync-fail.ts` 60초.

**이 리포에서는 한 번도 돈 적이 없다.** `.s9-sync` 마커 없음, `state/sync.log` 없음, 최근 커밋은 전부 리드의 수동 커밋(중앙값 간격 2225초). 따라서 아래 병목은 **격리 시뮬레이션과 코드 독해**로 낸 것이지 운영 실측이 아니다.

**브리프 정정 1건**: streams/ 는 이미 track 되지 않는다 — `.gitignore` 의 `streams/`(REQ-20260827-047), `SYNC_DATA_PATHS`(8391행)에서도 제외(REQ-20260827-077), `git ls-files streams` = 0. 두 겹 방어가 이미 서 있다. 반면 **state/sessions/ 는 track 중**(142파일 648KB)이고 바인딩은 프롬프트·클레임마다 다시 써진다(현재 세션 바인딩에 `agent_transcript_path` 10건 누적).

## ③ 권고안 — 2안 (main 단일 유지, 알고리즘을 고친다)

1. **커밋은 동기, 전송은 비동기.** 이벤트는 로컬 커밋(<0.3s)만 하고 반환. push·pull 은 serve 의 전송 스레드(serve 없으면 이벤트가 띄우는 분리 프로세스 1개)가 맡는다. 한 머신에 in-flight push 1개, 그 사이 쌓인 커밋은 한 push 에 묶인다 → "커밋 1 = 이벤트 1"(DOC-20260826-002 결론 A)은 지키고 push 수만 줄인다. 20인 규모에선 이 묶음이 선택이 아니라 천장 때문에 필수다.
2. **거부와 장애를 가른다.** non-fast-forward → 즉시 `fetch → rebase → push` 재시도(1·2·4·8·16s 지터, 최대 5회), 네트워크/타임아웃 → 60초 백오프. 재시도 소진은 "밀림" 상태로 표면화하되 커밋은 보존.
3. **문서 병합 드라이버**(`.gitattributes vault/**/*.md merge=s9doc`, 드라이버 등록은 `s9-install` 이 git hook 과 같은 방식으로). 필드별 규칙: `updated`=max, `agents`·`contributions`·`relates`=합집합, Notes·History=타임스탬프 정렬 합집합, `status`·`assignee` 가 양쪽 다르면 **결정적 규칙**(담당자 머신 우선, 진 쪽 전이는 History 에 "동시 변경으로 무효화" 줄로 남김). 모든 머신이 같은 결과에 수렴하므로 사람이 충돌 프롬프트를 보는 일이 없다. 근원 해결은 `updated` 를 매 쓰기마다 갈아엎지 않는 것이지만, 그 한 줄이 없어도 삽입 지점 충돌은 남으므로 드라이버가 필요하다.
4. **수신 폴링.** serve 가 활성 세션 있을 때 10초, 유휴 60초 간격 `fetch` + ff 병합 + index rebuild(0.5s). 전이 직전엔 그 문서에 한해 fetch 1회(낡은 상태 위의 전이 방지). 남의 문서가 도착해도 실행은 4번 축(담당자·머신) 가드가 막는다 — 전송층은 도착만 책임진다.
5. **자가 치유.** 전송 시작 시 `.git/rebase-merge`·`rebase-apply` 잔재 → `rebase --abort`, autostash 잔재 → `stash pop`. 타임아웃 분기에도 abort.
6. **track 정리.** state/sessions 는 이벤트 커밋에서 뺀다 — 다른 머신이 필요한 것은 "누가 무엇을 맡았나"뿐이고 그것은 REQ frontmatter(assignee·machine)로 간다. 첨부는 ingest 압축, pull 타임아웃은 비동기 경로에서 30초.

**지연 목표**: 이벤트→내 로컬 커밋 0.3s · →origin 도착 p50 5s / p95 15s(5인), p95 30s(20인, 묶음 창 확대) · →남의 화면 p50 15s / p95 40s. "초 단위"는 git 전송층으론 불가 — 필요해지면 GitHub webhook→serve 알림(외부 도달 가능한 서버가 있을 때만, WSL 데스크톱은 보통 불가) 또는 SSE 허브가 다음 단계다.

**실패 시 사용자에게 보이는 것**: 대시보드 git 판(REQ-20260901-023)에 "마지막 보냄 12초 전 · 받음 8초 전 · 대기 3건" 한 줄. 밀림 60초 초과 → 주황, 5분 초과 → 붉은 줄 + 훅이 리드에게 `◈ 동기화 지연` 1회 주입, `s9 digest` 머리에 같은 줄. 결정적 규칙으로 진 전이는 문서 History 와 카드에 "동시 변경으로 무효화" 로 보인다. 로그는 `state/sync.jsonl`(단계별 ms·재시도·결과)로 바꿔 `s9 sync --stats` 가 p50/p95·거부율을 낸다 — 거부율 30% 초과 또는 p95 60초 초과가 묶음 창 확대/허브 검토 신호.

**회복 절차**: (a) 밀림 — 자동 재시도, 사람 개입 없음. (b) 드라이버가 못 푼 충돌 — 양쪽 본을 `state/sync-conflict/<id>.<machine>.md` 에 남기고 규칙 적용 후 진행(큐를 한 문서가 막지 않음), 수동은 `s9 sync resolve <id> --take mine|theirs`. (c) 이력 재작성·완전 분기 — 전송 중단 + 안내: 미전송 커밋을 `state/sync-rescue/*.patch` 로 뽑고(`s9 sync rescue`) 다시 clone. `reset --hard` 는 게이트가 막는 대로 절대 쓰지 않는다. (d) 롤백 — 머신별 `s9 sync --off`(local 모드), 커밋은 전부 로컬에 남아 유실 0.

**배포 순서(지루하게)**: 관측·분류(0단계) → 비동기+재시도 → 드라이버 → 수신 폴링 → track 정리. 카나리: 주인 머신 + 1대에 remote 모드 1주, `--stats` 로 거부율·p95 확인 후 팀 확대.

## ⑤ 다른 역할에게

- architect: `updated` 를 매 쓰기마다 갈아엎는 구조를 유지할 것인가(드라이버 규모 결정), 8안(머신별 append-only 이벤트 로그) 채택 여부.
- backend-developer: `status`+`status` 동시 전이의 결정적 규칙 — 담당자 우선이 맞는가, 그 전이가 무효화될 때 워처·클레임이 어떻게 되돌려지는가.
- security-engineer: 병합 드라이버는 `s9-install` 이 로컬 git config 에 심는 실행 코드다 — non-admin 인스턴스에서 신뢰 경계.
- designer/ux-writer: git 판의 "밀림·받음·대기" 한 줄과 "동시 변경으로 무효화" 문구.
- 미확인: D(타임아웃 중 rebase 잔재) 재현, GitHub 실제 push 시간(측정은 `ls-remote` 2.4s 만), ID 시퀀스 NNN 이 pull 로 들어온 남의 번호와 어떻게 섞이는지(suffix 로 파일명 충돌은 없음).
