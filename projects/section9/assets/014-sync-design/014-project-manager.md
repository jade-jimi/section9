## ② 단계(Phase) 정의

원칙: **가드를 먼저 한 곳으로 모으고(0·1), 그 다음 키를 바꾸고(2), 공유는 마지막에 켠다(3·5).** 공유를 먼저 켜면 F3 경로가 실제 사고가 된다.

| Phase | 완료 판정(goal) | 선행 · 이유 | 되돌림 |
|---|---|---|---|
| **P0 두 머신 하네스** | 한 머신에서 `S9_MACHINE=A`/`B` 두 S9_ROOT 가 공용 bare 리포로 sync 왕복하는 픽스처가 있고, "A 가 만든 반려 REQ 가 B 에 pull 되면 B 의 워처·`s9 next`·`s9 reopened` 셋 중 하나라도 집는다" 를 재현하는 **빨간 테스트**가 있다 | 없음. 이후 모든 단계의 검증 도구 | 테스트 파일 삭제로 완전 |
| **P1 귀속 게이트 단일화** | 세 경로(F2 ⓐⓑⓒ)가 하나의 판정 함수(가칭 `owned_here(meta)`)를 쓰고 P0 테스트가 녹색. 잠정 키 = 현행 `machine` 필드(스키마 변경 없음) | P0. 게이트가 한 곳에 있어야 P2 에서 키만 바꾸면 된다(핵심가치 ③ 단일 게이트) | 함수 하나 되돌리면 끝 — 문서 무변경 |
| **P2 생성자·담당자 모델** | 새 문서에 `creator`(user) · `assignee`(user) · `origin`(human / agent:<역할> / derived:<REQ>) 이 기록되고, 기존 846 문서는 **읽기 시 기본값**(creator=assignee=user, origin=human)으로 해석되며, `s9 assign <id> <user>` 로 담당자가 바뀌고 P1 게이트의 키가 `assignee` 로 바뀐다 | P1. 키 교체는 게이트가 한 곳일 때만 안전 | 필드 추가라 하위 호환. 게이트 키를 machine 으로 되돌리는 스위치 유지 |
| **P3 동기화 강화** | sync 가 on 인 두 위장 머신이 각 100 이벤트를 동시에 쏴도 유실 0 · 수동 충돌 해결 0 · 이벤트당 p95 < 3s (수치는 결정 D2 후 확정) | P0(하네스). P2 와 **병행 가능** — 파일 경로가 다르다 | `s9 sync --off` 로 즉시. 브랜치 전략을 바꿨다면 되돌림 비용 큼(D2 참조) |
| **P4 observer 강제** | viewer 역할 사용자가 CLI(new/status/note/assign)와 서버 쓰기 API 모두에서 거부되고, 조회·검색·이력·지식은 전부 된다는 테스트 매트릭스가 녹색 | 없음 — P1~3 과 **독립·병행**. DOC-20260823-005 2단계를 여기서 흡수 | 게이트 off 스위치 |
| **P5 실머신 검증 · 기본값 전환** | 실제 두 번째 머신(또는 WSL 두 계정)에서 P0 시나리오 + 담당자 이관 + observer 를 사람이 재현해 승인. 그 뒤 sync 기본 정책 결정 | P1·P2·P3·P4 전부 | 기본값 off 로 되돌림 |
| **(보류) vault 분할** | — | 결정 D3 에서 사용자가 고르기 전까지 착수하지 않는다 | 846 파일 git rename — 되돌림 비용 최대 |

## ⑤ 사용자가 판정할 결정 항목 (review 확인 포인트 형태, 300자·3갈래 이내)

**D1 실행 귀속 키** — 남의 요청이 내 컴퓨터에 내려와도 내 컴퓨터가 손대지 않게 하는 기준입니다. ㉠ 지금처럼 「문서를 만든 컴퓨터」 ㉡ 「담당자」(같은 사람이면 어느 컴퓨터든) ㉢ **권고: 「담당자 + 처음 집은 컴퓨터」** — 담당자를 바꾸면 넘어가고, 같은 사람의 두 컴퓨터가 동시에 집는 일(R6)도 막힙니다. ㉠은 할당이 불가능, ㉡은 두 컴퓨터 중복 위험.

**D2 공유 방식(브랜치)** — ㉠ **권고: main 하나 + 이벤트 sync 강화**(현행 구조 유지, 문서는 append 위주라 rebase 충돌이 드묾, 되돌림 쉬움) ㉡ 프로젝트별 브랜치(통합 조회를 위해 매번 여러 브랜치를 merge 해야 해 "지저분하지 않게" 조건과 충돌) ㉢ 프로젝트-사용자 브랜치(브랜치 수 = 사람×프로젝트, 담당자 이관 때마다 브랜치 간 이동). ㉡㉢은 되돌림 비용이 가장 큽니다.

**D3 vault 디렉토리 분할** — ㉠ **권고: 유지**(846건 전체 인덱스 0.19초 — 조회 성능은 이유가 못 되고, 분할은 846 파일 rename + 첨부·링크 경로 재작성) ㉡ 프로젝트별 ㉢ 프로젝트/사용자별. 분할이 주는 실이득은 "git 충돌 표면 축소" 하나인데 파일 단위 문서라 이미 표면이 작습니다. 사용자가 ㉡㉢을 고르면 L 크기 REQ 하나가 추가됩니다.

**D4 observer** — ㉠ **권고: 기존 viewer 역할을 강제**하고 화면 낱말만 「관찰자」로(새 역할 추가 없음, DOC-20260823-005 2단계와 합침) ㉡ observer 를 네 번째 역할로 신설(viewer 와 무엇이 다른지 정의해야 함) ㉢ 계정이 아니라 읽기 전용 대시보드 URL 토큰. ㉢은 검색·이력까지 주려면 결국 계정이 필요합니다.

**D5 기존 문서 처리** — ㉠ **권고: 읽을 때 기본값 채움**(생성자=담당자=user, 출처=사람; 파일 무변경, 사고 R2 회피) ㉡ 846건 일괄 rewrite(한 커밋, sync off 에서) ㉢ 레거시 ID 227건 rename 까지 포함. ㉠으로 시작하고 ㉢은 실충돌이 생길 때만.

**D6 에이전트 파생 요청의 담당자 기본값** — 에이전트가 남의 요청을 처리하다 만든 요청의 담당자는 ㉠ **권고: 원 요청의 담당자**(출처 REQ 를 따라감 — "내 요청으로 파생된 것만 내 컴퓨터가 처리") ㉡ 에이전트를 돌린 세션의 사용자 ㉢ 비워 두고 사람이 배정. ㉠㉡은 리드가 남의 요청을 처리하는 경우에만 갈리고, 그 경우는 D1 ㉢ 아래에서 담당자 이관이 먼저 일어나야 하므로 사실상 같습니다.
