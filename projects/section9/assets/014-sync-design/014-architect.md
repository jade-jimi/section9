## 1. 현황 진단 (코드·실험으로 확인한 사실)

- **F1 네트워크가 이벤트 경로 안에 있다.** `maybe_sync` 는 new/전이/note/link/set/assets/rm 등 10곳(bin/s9:1535, 1855, 8786, 8826, 9924, 12245, 12791, 12879, 12908, 12943)에서 **CLI 프로세스 안에서 동기적으로** `add → diff → commit → pull --rebase --autostash(8s) → push(8s)` 를 돈다(sync_run 8506~8590). History 줄 수로 센 문서 이벤트는 2026-09-01 767건, 08-28 1464건 — remote 모드면 그 횟수만큼 원격 왕복이 명령 지연에 얹힌다.
- **F2 "busy" 는 이벤트를 버린다.** 락이 30초 미만이면 `return "busy"`(8519) — "그쪽이 함께 실어 감"이지만 그쪽의 `add -A` 는 이미 지나갔을 수 있어, 그 변경은 **다음 이벤트가 올 때까지** 로컬에만 남는다. 지연 상한 없음.
- **F3 주기 pull 이 없다.** `sync_run` 호출자는 `maybe_sync` 와 `cmd_sync` 뿐(8521, 8595, 8629). 이벤트를 안 내는 머신은 남의 변경을 **영원히** 못 본다. 화면의 pull 손잡이(REQ-20260901-023, 16733)는 `pull --ff-only` — sync_run 의 `pull --rebase` 와 **pull 경로가 둘**이다.
- **F4 충돌 = 조용한 영구 정지.** pull 실패 시 `rebase --abort` 후 로그만 남기고 반환(8560~8566). 로컬 커밋은 남아 있으므로 다음 이벤트의 pull 도 같은 커밋에서 다시 충돌한다. 복구 명령이 없고, 화면 표시도 없다(state/sync.log 뿐).
- **F5 충돌 면적은 디렉토리가 아니라 프론트매터다.** 스크래치 클론 셋으로 실험(scratchpad/014/conf): 같은 REQ 를 A 가 note(Notes 끝 삽입 + `updated`), B 가 전이(`status`/`status_since`/`updated` + History 끝 추가) → **rebase 충돌**(rc=1, 프론트매터 18~24행). 반면 C 가 History 만 덧붙인 경우(프론트매터 불변) → **깨끗이 병합**(rc=0). 즉 모든 쓰기가 갱신하는 `updated`(1527, 1742, 8732~8779, 12227 등 15곳)와 `agents/contributions/children/relates/blocked_by` 리스트가 충돌의 원인이다. 문서 하나에 두 머신이 손대면 **거의 항상** 충돌한다.
- **F5' 남의 파일을 쓰는 경로가 있다.** `s9 new --parent` 는 부모 문서의 `children`+`updated` 를 고쳐 쓴다(1522~1528). `s9 link --relates` 는 상대 문서도 쓴다(8744~8779). `blocked_by` 자동 해제도 다른 문서를 쓴다(8340). `users/<u>/profile.md` 의 `machine_accounts` 줄은 주간 22회 재기록(git log 실측), 프로젝트 문서 `members` 도 공유 쓰기다. 따라서 "자기 문서만 자기 머신이 쓴다"는 규율만으로는 면적이 0이 되지 않는다.
- **F6 머신 간 클레임이 보이지 않는다.** `rework_claimed`(3517)는 `state/*.json` 을 전부 읽으므로 pull 된 남의 바인딩도 읽지만, 생존 판정 `chat_live` 가 로컬 pid·transcript 경로를 요구해 **남의 머신 클레임은 항상 죽은 것으로** 판정된다. 중복 스폰을 막는 것은 `meta.machine != current_machine()`(7247) 하나 — **생성 머신** 기준이라, 담당자를 바꾸면 스폰이 영영 안 되거나(생성 머신이 꺼짐) 엉뚱한 머신이 집는다. `next_pickup`(11002)은 user 로만 거른다.
- **F7 ID 는 이미 무합의 전역 유일.** `next_id`(946~): `PREFIX-YYYYMMDD-NNN-<머신지문4>` — 순번은 지문이 같은 파일만 센다. 파일명 충돌은 구조적으로 없다(docs/08 "알려진 한계 1"은 낡음).
- **F8 파생 인덱스는 싸다.** `s9 index rebuild` 0.28s(846건 실측), 대시보드 신선도는 catalog stat 지문(590). `pull --rebase` 도 post-checkout 훅을 부른다(git 2.43 실험: post-checkout·post-rewrite 발화) → pull 뒤 화면 갱신은 이미 된다.
- **F9 전제 정정.** streams 는 track 하지 **않는다**(.gitignore, SYNC_DATA_PATHS 8391 주석) — docs/08 표와 브리프의 "streams 도 track 중"은 낡은 서술. 동기화 대상은 vault·users·projects·state/sessions·.s9-sync 다.
- **F10 크기.** .git 204MB, vault 99MB(대부분 assets PNG). 이벤트 커밋에 캡처가 실린다 — 전송량은 텍스트가 아니라 그림이 결정한다.

## 3. 권고안 — "① 유지 + 쓰기 모델 수리" (세 겹)

**결정:** 브랜치·허브·디렉토리는 손대지 않는다. 단일 main 위에서 (A) 이벤트 경로에서 네트워크를 떼어 serve 가 동기화를 소유하고, (B) 문서 형식을 아는 **git merge driver** 로 같은 문서의 동시 쓰기를 결정론적으로 병합하며, (C) 실행 귀속을 생성 머신이 아니라 **담당자**로 옮긴다. 세 요구를 동시에 만족하는 조합은 이것뿐이다: ②③은 실시간을, ⑤는 오프라인을, ④⑥은 호환·원칙을 깬다.

**A. 동기화의 소유자 = serve (F1·F2·F3 해결).**
- 이벤트 경로는 파일을 쓰고 `state/sync.queue` 에 한 줄 남기고 끝난다(≤ 50ms). serve 의 동기화 루프가 **디바운스 2초로 commit**, 성공 시 push, 그리고 이벤트와 무관하게 **15초마다 fetch**(변경 있을 때만 pull). 유휴 머신도 p95 30초 안에 남의 변경을 받는다.
- serve 가 없는 자리(제한 워커·CI)는 지금의 인라인 경로를 유지하되 `--no-wait` 기본. pull 경로는 하나로 통일 — 화면 손잡이도 같은 함수를 부른다(F3 둘째 결함).
- 오프라인: 지금처럼 로컬 커밋 누적 + 백오프. 달라지는 것은 **화면에 "n건 미전송 · 마지막 성공 hh:mm" 이 항상 보인다**는 점.

**B. 문서 병합 드라이버 (F4·F5 해결) — ④의 의미론을 저장이 아니라 병합 시점에.**
- `.gitattributes`: `vault/**/*.md merge=s9doc`, `users/*/profile.md`, `vault/projects/*.md` 동일. `s9-install` 이 `git config merge.s9doc.driver "s9 merge-doc %O %A %B"` 를 등록(훅과 같은 설치 경로·같은 한계 — 미설치 머신은 지금과 같은 충돌로 떨어지지 되돌아가지 않는다).
- 규칙(결정론, 3-way): 프론트매터 스칼라는 `updated` 가 늦은 쪽; 리스트(`agents/children/relates/tags/blocked_by/contributions/machine_accounts/members`)는 합집합; `## Notes`·`## History` 항목은 타임스탬프 헤더 단위로 **합집합 후 시각순**. `status` 가 양쪽에서 달리 바뀐 경우만 "의미 충돌" — 늦은 쪽을 취하고 History 에 두 줄 다 남기며 `s9 doctor` 가 「이중 전이」로 표시(사람 판정 1건으로 축소).
- 실험 case1(note vs 전이)이 자동 병합되는 것이 회귀 시험의 기준.
- 부수 효과: `pull --rebase` 도 merge driver 를 쓰므로 sync_run 의 abort 경로는 "드라이버도 못 푼 것"에만 남고, 그때는 **화면에 diverged 표시 + `s9 sync --resolve`** 로 복구 명령을 준다(지금은 명령이 없다).

**C. 실행 귀속 = 담당자 (F6 해결, backend 축과 접점).**
- frontmatter 에 `assignee`(기본 = creator) 를 두고, 워처·`next_pickup`·훅 주입은 `assignee == me` 만 본다. 머신 가드(7247)는 "담당자의 활성 머신"으로 바꾼다 — 담당자 한 사람이 머신 둘이면 `state/sessions` 바인딩(track 됨)에 적힌 클레임을 인정하되, `chat_live` 대신 **바인딩의 `claim_at` 신선도(예: 2분)** 로 원격 생존을 판정한다(로컬 pid 는 원격에 없다).
- 이로써 남의 in-progress 가 pull 돼 와도 내 머신은 집지 않고, 할당은 `assignee` 한 필드 변경(=문서 이벤트=동기화)으로 끝난다.

**교차 쓰기 축소(B 를 가볍게 하는 보조):** `children` 은 부모 파일에 쓰지 않고 catalog 에서 파생(자식의 `parent` 가 원천 — 단일 쓰기 경로), `updated` 는 마지막 History 시각에서 파생. 두 가지가 F5' 의 절반을 없앤다. 선택이지만 권한다.

**예상 결과:** 이벤트 지연 -네트워크(초 단위 → ms), 유휴 머신 전파 ∞ → ≤ 30s, 충돌은 병합 규칙으로 흡수되어 사람 개입은 "이중 전이" 뿐, 동기화 정지는 화면에 드러난다. 비용: 병합 드라이버 구현·시험(가장 큰 덩어리, 문서 포맷 파서는 fm_parse/fm_dump 재사용), serve 에 루프 하나, 설치 항목 하나.

## 5. 다른 역할에게 넘기는 질문 · 열린 문제

- **backend**: `assignee` 변경 권한(본인·admin·프로젝트 maintainer?)과 훅 주입(s9-audit-prompt)의 REQ 필터가 user 인지 assignee 인지 — 원격 바인딩 생존 판정을 `claim_at` 신선도로 바꿔도 되는지(REQ-20260826-013 의 "바쁜 세션이 클레임을 잃는" 사고와 상충 여부).
- **product-owner**: 이중 전이(리뷰어 승인 vs 담당자 반려가 동시에)의 정답 — LWW 로 두고 doctor 표시로 충분한가.
- **security-engineer**: viewer(ROLES 13147, 이미 존재)의 read-only 를 serve 가 강제하는가(`viewer_of` 17394) — 그리고 origin 에 **push 권한이 있는 사람은 누구나 남의 문서를 고칠 수 있다**는 git 층의 사실을 어디까지 막을지(서버측 branch protection 은 파일 단위 인가를 못 한다).
- **devops**: Windows(`bin\s9-install.cmd`)에서 merge driver 등록·`%O %A %B` 경로 처리; 미설치 머신 감지(`s9 doctor`).
- **quality-assurance**: 다중 클론 시험 하네스(scratchpad/014/conf 의 셋업을 tests/ 로) — case1 자동 병합·유휴 머신 전파·오프라인 복귀 시나리오.
- **미확인**: 훅 주입이 machine 으로 거르는지(grep 상 s9-audit-prompt 에 machine 필터 없음 — 실행 경로는 안 읽음), remote 모드 인스턴스에서의 실제 이벤트 지연 수치(이 카피는 코드 리포라 `.s9-sync` 없음 — 실측 불가).
