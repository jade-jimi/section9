### 2026-08-26T19:36:13+09:00 answer (agent: sub:architect, by sjpark1)

**쓰지 않는다.** 확인한 사실 (2026-08-26 13:06):

- 코드 전체에 `crontab`/`systemctl` 호출 0건. 이 계정 crontab 비어 있음.
- `bin/s9-doctor` 의 "systemd" 문자열은 *부모가 init/systemd/launchd 면 고아로 본다*는
  판정용이지 사용이 아니다.
- 이 머신 `~/.config/systemd/user` 의 harness-tick·claude-oom-guard 유닛은 section9 것이
  아니고 우리 코드가 건드리지 않는다.

그래서 **외부 스케줄러 도입 금지**를 제약으로 확정했다 — systemd(user) 유닛도 cron 항목도
만들지 않는다. 감시는 자기 감시 방식으로 간다: `s9 serve` 가 감시자를 분리 기동(setsid +
double-fork)해 사용자 세션과 무관하게 살아남고, 감시자까지 사라지는 경우(WSL 재시작)는
SessionStart 훅이 멱등하게 다시 세운다. 백오프를 둔다.

기각한 대안: systemd user 유닛(사용자가 명시적으로 배제, 이 셸에서 user 버스 연결도 안 됨),
cron(같은 이유). 둘 다 "의존성 0" 원칙과도 어긋난다.

### 2026-08-26T19:40:25+09:00 answer (by sjpark1)

쓰지 않는다. 확인한 사실은 셋이다.

1. 코드 전체에 `crontab` · `systemctl` 호출이 0건이다. `bin/s9-doctor` 에 나오는 "systemd" 문자열은 *부모 프로세스가 init/systemd/launchd 면 고아로 본다*는 판정용이지 사용이 아니다.
2. 이 계정의 crontab 은 비어 있다.
3. 이 머신의 `~/.config/systemd/user` 에 harness-tick · claude-oom-guard 유닛이 있으나 section9 것이 아니고 우리 코드가 건드리지 않는다.

감시는 외부 스케줄러가 아니라 `s9 serve` 의 데몬 스레드가 맡는다. 이후 설계도 이 제약 위에 선다 — REQ-20260825-096-62x6(대시보드 자동 복구)은 systemd user 유닛과 cron 을 둘 다 기각하고 **자기 감시**(setsid + double-fork 로 분리 기동한 감시자 + SessionStart 훅의 멱등 재수립 + 백오프)로 간다. 기각 이유는 이 답 그대로다: 사용자가 명시적으로 배제했고, 이 셸에서는 systemd user 버스 연결도 되지 않으며, 둘 다 "의존성 0" 원칙과 어긋난다.

(원 답변 시각 2026-08-26 13:06. 그때 이 답은 REQ-20260825-096-62x6 노트에만 있었고 — 2시간 뒤 사용자가 "답변을 했었나"라고 다시 물었다. 이 문서가 그 재발을 막으려고 생긴 타입의 첫 사례다.)
