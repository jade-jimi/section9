permission도 하네스 내부에서 미러를 뜨고 있다가 다른 머신에 가서도 덮어쓸 수 있게 하는건 어때? git push origin main 이 명령어는 실행했다.

**푸시 확인했다.** `origin/main` 이 로컬과 같은 `c16d407` 이다. **문서 444건이 이제 이 컴퓨터 밖에도 있다.** 034 닫았다 — 오늘 아침부터 백업이 없던 상태가 해소됐다.

### 설정 미러 — 좋은 생각인데, 권한만은 다르다

**옮길 값이 있는 것**은 분명하다. 머신을 바꾸면 지금 `model`·`theme`·`remoteControlAtStartup`·`env` 같은 게 전부 날아간다. 훅은 이미 `s9-install` 이 재생성하니 옮길 필요가 없고, 나머지는 미러해서 복원하면 그대로 이득이다.

**그런데 `permissions` 는 그대로 옮기면 안 된다. 그 이유가 방금 우리가 겪은 일이다.**

게이트가 오늘 두 번 막았다. ① `git push` ② **그 push 를 허용하도록 settings.json 을 고치는 것.** 두 번째가 핵심이다 — 막힌 능력을 스스로 열도록 설정을 고치는 동작이라 막힌 거다.

**제안하신 구조는 그 두 번째를 우회하는 길을 만든다.** 제가 vault 에 쓰면(안 막힌다) → 동기화되고 → 다른 머신이 그걸로 settings.json 을 덮는다. **이 머신에서 막힌 걸 저 머신에서 여는 셈이다.** 의도가 아니어도 구조가 그렇다.

한 겹 더 있다. 이 리포는 **공개**다. 권한 파일이 vault 에 실려 흐르면 "어느 머신이 무엇을 자동 허용하는가"가 공개 기록이 된다. 그건 설정이 아니라 **공격 표면 지도**다.

**그래서 이렇게 가르기를 제안한다** (REQ-20260827-045-62x6):

| | |
|---|---|
| **자동 복원** | model · theme · env · UI 취향 — 위험 없음 |
| **수동 승인** | permissions — 옮기되 적용은 사람이 |
| **안 옮김** | 자격증명·토큰 — 비밀값 자리(035)로 |

`permissions` 는 미러는 하되 **자동 적용하지 않는다.** 새 머신에서 `s9 config apply` 를 부르면 **무엇이 달라지는지 diff 로 보여주고**, 권한 항목은 따로 세워 "이 명령들을 자동 허용하게 됩니다"라고 적고 `--yes` 를 요구한다.

**권한을 옮기는 것 자체는 반대하지 않는다. 말없이 덮는 것에 반대한다** — 그건 게이트를 옮기는 게 아니라 없애는 거다.

이 방향으로 진행할까? 아니면 permissions 도 자동 복원으로 갈까?
