## 전제 변화
공개 리포(github.com/nicehugepark/section9)는 코드 전용이 됐다(.gitignore로 vault/users/projects/streams/state 제외). docs/08의 "모든 것을 한 사설 리포에 track" 전제는 더 이상 성립하지 않는다 — 코드(공개)와 데이터(사설)의 분리가 필요하다.

## 1. 리모트 구성 (권고: dual-repo)
- **코드**: 현행 origin(공개) 유지. 푸시 주체는 리드 세션(작업 완료 시).
- **데이터**: 사설 리포 `section9-vault`(private, 팀 공유)를 **같은 디렉토리의 두 번째 git**으로 운영 — `GIT_DIR=~/.section9-data.git`, work-tree=~/section9. 추적 대상: vault/ users/ projects/ streams/ state/sessions/. 코드 경로는 info/exclude로 반대 방향 무시. 공개 리포와 완전 격리(상호 오염 불가), 디렉토리 재배치 없음.
- 관리 명령: `s9 sync [--push|--pull|--status]` 신설. 새 머신 셋업: clone(코드) → s9-install → s9 sync init(사설 리포 연결).

## 2. 푸시/풀 주기 (권고 값)
- **push = 이벤트 기반 + 디바운스 30초**: 문서 쓰기 경로(do_transition·note·new·user config)가 dirty 마크만 남기고, serve의 워처 스레드가 30초 배치로 commit+push. 쓰기마다 push하면 히스토리·네트워크 낭비, 주기가 길면 협업 지연 — 30초가 절충.
- **pull = serve 60초 fetch + ff/rebase, SessionStart 1회**: post-merge 훅이 index rebuild(기존 자동화 재사용). 유휴 시(최근 쓰기 없음) 5분으로 완화하는 가변 주기.
- 체감 동기화 지연: 상대 push 디바운스(≤30s) + 내 pull(≤60s) = **최악 ~90초, 통상 1분 미만**.

## 3. 실시간(초 단위) 협업이 필요해지면
- a) pull 가변 주기 강화(활동 감지 시 10초) — 추가 인프라 0. 우선 적용 권고.
- b) 대시보드 허브: 한 serve를 LAN에 열고(인증 필수) 타 머신 대시보드가 SSE 구독 — 로컬 파일 원칙 훼손·단일 장애점. 실수요 확인 후.
- c) GitHub webhook은 공인 IP 필요라 로컬 하네스에 부적합.

## 4. 충돌·용량 전략
- vault 문서는 1문서=1파일·append 위주라 충돌 면적 최소. rebase 실패 시 s9 sync가 중단하고 대시보드에 ⚠ 배지 + blocked 로그(자동 해결 시도 금지).
- ID 시퀀스 충돌(같은 날 오프라인 두 머신)은 docs/08 한계 그대로 — 잦아지면 REQ-YYYYMMDD-<m>-NNN 스킴 전환.
- streams는 세션당 수 MB — 사설 리포에서도 90일 경과분 아카이브 정책 필요(후속).
- state/sessions는 파일 키에 machine 포함이라 머신 간 충돌 없음. chat inbox(state/chat)는 머신 로컬 — 동기화 제외.

## 5. 단계별 도입
1단계(즉시 가능): s9 sync 수동 명령 + SessionStart pull. 2단계: serve 자동 push/pull 스레드(위 주기). 3단계: 가변 주기·아카이브. 승인 시 1·2단계를 함께 구현한다.
