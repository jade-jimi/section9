## Original

수십 명이 git으로 동시 사용 시 vault 비대화/충돌 우려에 대한 검토 (요청: REQ-20260823-006).

**현황 진단**: 디렉토리 비대화는 YYYY/MM 파티션이 이미 완화. 실제 리스크는 (a) 서로 다른 사용자/머신이 같은 날 오프라인에서 문서 생성 시 REQ-YYYYMMDD-NNN 시퀀스 충돌(같은 파일명 → git 충돌), (b) 수십 명 규모에서 월 디렉토리당 파일 수백~수천 개.

**안 1 — user 파티션 + user 포함 ID** (`vault/requests/{user}/YYYY/MM/REQ-{user}-YYYYMMDD-NNN.md`)
- 장점: ID/파일명 충돌 원천 제거(시퀀스가 사용자별), 사용자 단위 공간/보존 정책 가능, git 충돌 면적이 사용자별로 격리, "자기 요청 위주로 본다"는 사용 패턴과 저장 구조 일치.
- 단점: ID가 길어짐, 기존 문서 마이그레이션 필요(파일 이동 + ID rename + parent/relates 참조 갱신 + rebuild).

**안 2 — 경로만 user 파티션, ID 유지**: 다른 사용자가 같은 날 같은 시퀀스를 만들면 ID 유일성이 깨져 find/link가 오동작 → 탈락.

**안 3 — ULID/랜덤 ID**: 충돌은 사라지나 사람이 읽고 부를 수 없는 ID는 "사람이 읽는 md" 철학과 상충 → 탈락.

**권고**: 안 1을 채택하되 지금은 아니다. 현재 규모(사용자 1~3명)에서는 마이그레이션 비용 > 이득이고, git이 충돌을 잡아주므로 데이터 유실 위험도 없다. **채택 트리거**: ① 실제 ID 충돌 1회 발생, 또는 ② 상시 사용자 5인 이상. 트리거 도달 시 마이그레이션 스크립트(단순 rename+참조 갱신)와 함께 전환한다.

### v2 — 신원 자동 파생(whoami) 설계 검토 (2026-08-24, REQ-20260824-025)

### 사용자 지적의 타당성 검증
'자기 계정 하나뿐인데 선택하는 것 자체가 모순, 머신도 입력할 일이 아니라 파생 가능한 사실' — 타당하다. 근거:
- 터미널 쪽 신원은 이미 파생이다: resolve_user()가 세션 바인딩→$S9_USER→OS 계정 순으로 자동 결정하고, 사용자는 아무것도 고르지 않는다.
- 대시보드만 예외적으로 '자기신고 셀렉터'를 요구해 왔다. 그런데 대시보드는 127.0.0.1 전용이므로 브라우저 앞의 사람 = 이 머신의 OS 계정 사용자 = 서버를 기동한 계정과 사실상 동일인이다. 서버는 그 계정과 hostname을 이미 안다. 즉 셀렉터는 서버가 아는 사실을 사람에게 되묻는 UI였다.

### 제안: whoami 모델 (선택 → 파생)
1. 서버가 기동 시점에 신원을 확정: os계정 → users/ 프로필 매칭(등록 시 os_account를 프로필에 자동 저장, 기존 계정은 registered_on·바인딩 이력으로 1회 역추론) → GET /api/whoami = {user, display, role, machine}.
2. 대시보드는 셀렉터 대신 **표시 전용 라벨** 'sjpark1 @ DESKTOP-TEHV1KR [admin]'. localStorage s9me 폐기.
3. 쓰기 경로의 actor를 클라이언트 self-report(user 파라미터)에서 **서버 파생으로 전환** — 클라이언트가 보낸 user는 무시. 자기신고 스푸핑 표면 자체가 줄어든다(가드레일→반보 전진, 단 인증은 여전히 아님).
4. 열람 격리(REQ-017)·개인화(pref/스킨)도 whoami 기준으로 동일 동작. me 전환 UI 소멸로 '남 계정 고르기' 경로도 소멸.

### 실패 모드와 대응
- F1 미등록 OS 계정: 대시보드가 배너로 's9 user add <이름>' 안내(자동 등록은 하지 않음 — 이름 오염 방지).
- F2 OS 계정명 ≠ s9 계정명(머신마다 계정명이 다른 로밍): 프로필 os_account를 다중값으로 — 새 머신에서 최초 1회 's9 user attach <이름>' 하면 현 OS 계정이 alias로 연결. 이후 그 머신에서도 자동 파생. (선택 UI가 아니라 1회 CLI 연결)
- F3 한 OS 계정을 여러 사람이 공유: 파생 불가 명시적 한계 — 이 경우에만 Settings 안 '대리 조작'(admin 전용, 상시 비노출)으로 예외 처리. 상시 셀렉터는 제거.
- F4 대시보드를 외부에 여는 경우(0.0.0.0): whoami 모델도 무력 — 실인증(PIN/토큰) 필수 경계는 기존 결론 유지.

### 마이그레이션
me 셀렉터·s9me 제거 → whoami 라벨, API의 ?me=/user: 서버 파생으로 대체(과도기: 파라미터 수신 시 무시+로그), 훅·격리·live 로직 영향 없음(모두 서버/CLI 파생 기반). 문서(가이드 4·5장, me 격리 문단) 동반 개정.
