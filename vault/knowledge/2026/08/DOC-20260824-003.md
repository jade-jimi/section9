## 구조 (권장)
- **section9 리포 = 업스트림(프레임워크)**: 하네스 코드만(bin/web/harness/docs/tests). 개선은 여기서만.
- **별도 리포 = 인스턴스(작업 공간)**: section9을 클론해 시작, vault/users/projects 등 데이터를 track(사설). 프로젝트 관련 설정·문서는 전부 여기.
- 인스턴스는 두 리모트를 가진다: origin(인스턴스 사설 리포) + upstream(section9).

## 업그레이드 플로우 (인스턴스에서)
1. `git fetch upstream && git merge upstream/main`
2. post-merge 훅이 자동으로 `s9 index rebuild` + `s9-install --quiet` — 훅/스킬/에이전트 최신화까지 자동.
충돌이 안 나는 이유: 데이터 파일은 업스트림에 없고, 코드 파일은 인스턴스에서 수정하지 않는 규율(pre-commit s9-guard + CODEOWNERS가 강제) — 교집합이 없어 머지가 항상 깨끗하다.

## 하네스 개선 플로우 (업스트림으로 역류)
인스턴스 작업 중 하네스 결함 발견 → 인스턴스에서 고치지 말고 section9 작업 카피(개발 인스턴스)에서 수정·테스트·푸시 → 각 인스턴스는 다음 merge로 수령. 실수로 인스턴스에서 코어를 고치면 guard가 비admin 커밋을 차단하고, admin이면 업스트림에 cherry-pick 후 인스턴스는 merge로 정렬.

## 인스턴스 초기화 절차
```
git clone <section9-url> ~/acme-s9 && cd ~/acme-s9
git remote rename origin upstream
git remote add origin <사설 인스턴스 리포>
.gitignore에서 데이터 경로(vault/ users/ projects/ streams/) 제외 해제   # 데이터 track
bin/s9-install && git push -u origin main
```

## 발전 단계 (인스턴스가 늘어나면)
지금은 위 git 머지 플로우로 충분(추가 도구 0). 인스턴스가 여러 개 되고 버전 관리가 필요해지면: 업스트림에 태그 릴리즈 + `s9 upgrade`(코드 경로만 태그 기준으로 갱신·커밋하는 명령) 도입 — 머지 이력 없이 패키지 매니저식 업그레이드.

## REQ-048(동기화 설계)과의 관계
이 구조가 048의 "단일 vs dual" 질문을 해소한다: **데이터는 인스턴스 리포가 track**(사설), section9은 코드 전용 유지. 048의 push/pull 주기 설계는 인스턴스 리포에 적용된다.
