## Original

우선 지금 상태 기준으로 커밋과 푸시를 먼저 해줘. 상당히 많은 부분이 변경이 될 거라 스냅샷을 찍어둘 필요가 있다. 
그리고 답변이다. 답변 전에 커밋,푸시를 하고 내 답변을 읽도록 해.

D1 실행 귀속 키: ㉠ 담당자 + 처음 집은 머신(문서 리스) — 권고 / ㉡ 담당자만(두 머신 중복 위험) / ㉢ 지금처럼 만든 머신(할당 불가).
 -> ㉡ 담당자만으로 하는게 좋을 것 같긴 한데 권고대로 ㉠으로 가도 좋다. 단, 사용자는 자신의 요청 문서에서 실행될 머신을 변경할 수 있어야겠지?
    그래야 다른 머신에서도 이어서 진행할 수 있다. 그렇지 않으면 처음 머신이 꺼지고, 다른 머신 사용 시 요청을 처리할 방법이 없어진다.
    이걸 고려하면서 다시 설계를 하거나, 기능이 추가되거나 해야겠다. 이 또한 내 의견일 뿐 방향을 제시했다기 보단 검토 사항 중 하나다.
D2 담당자 필드 이름: ㉠ user 를 담당자로 재정의 + creator 추가 — 권고 / ㉡ 새 assignee 추가, user 는 생성자 유지(읽는 자리 넷 수정).
 -> 권고대로
D3 공유 방식: ㉠ main 하나 + 쓰기 모델 수리 — 권고 / ㉡ 프로젝트별 브랜치 / ㉢ 프로젝트-사용자 브랜치.
 -> 권고대로
D4 vault 배치: ㉠ 유지 — 권고 / ㉡ 프로젝트별 / ㉢ 프로젝트/사용자별(L 크기 추가, 이력 단절).
 -> 권고대로
D5 observer: ㉠ viewer 강제 + 화면 낱말만 「관찰자」 — 권고 / ㉡ 네 번째 역할 신설 / ㉢ 읽기 전용 URL 토큰.
 -> 권고대로
D6 기존 문서: ㉠ 읽을 때 기본값(파일 무변경) — 권고 / ㉡ 846건 일괄 rewrite / ㉢ 레거시 ID 230건 rename 포함.
 -> 권고대
D7 세션 바인딩 공유: ㉠ track 해제(리스가 대체) — 권고 / ㉡ 유지하되 로컬 필드 분리·판정에서 무시.
 -> 이해를 못했다. 설명 필요
D8 상태 동시 변경 규칙: ㉠ 늦은 쪽 + 양쪽 History + doctor 표시 — 권고 / ㉡ 담당자 머신 우선.
 -> 이해를 못했다. 설명 필요
