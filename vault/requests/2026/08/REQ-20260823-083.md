### 재설계 (클레임 기반 워처)
**결함**: 기존 흐름은 반려 '전이 시점'에 1회만 판정 — 담당 세션이 살아있으면 스폰을 생략하고 '라이브 세션이 다음 프롬프트에서 집는다'에 의존. 트리거가 사용자 발화라서, 사용자가 '진행해'라고 말하는 것과 동치. 자동화가 아니다.

**원칙**: 반려는 이벤트다. 진행 보장은 사람 발화와 무관해야 한다. 세션의 '생존'이 아니라 **'클레임'(실제로 집었는가)** 이 판정 기준이다.

**설계**:
1. 클레임 = 어떤 신선한(2분 내 활동) 세션의 last_req/active_reqs에 그 REQ가 등록됨 — live 표시(REQ-20260823-080/082)와 동일한 primitive. 표시와 진행 판정이 한 개념을 공유한다.
2. 반려 전이 시점에는 스폰하지 않는다 (PENDING 로그만). 유일한 진행 경로는 워처.
3. **워처**: serve 프로세스(반려가 발생하는 곳이므로 반려 시점에 반드시 살아있음)의 데몬 스레드가 30초마다 스캔 — status=in-progress이고 마지막 전이가 review→in-progress(반려)인 REQ 중:
   - 유예(auto_resume_grace_sec, 기본 90초) 이내 → 대기 (라이브 세션/기존 위임이 집을 기회)
   - 클레임됨 → 손대지 않음
   - 유예 경과 + 미클레임 → 무인 스폰:
     · 담당 세션이 조용함 → 기존처럼 headless --resume (컨텍스트 승계)
     · 담당 세션이 살아있는데 안 집음 → **새 headless 세션** 스폰 (활성 세션 포크 금지 — REQ-20260823-081). 컨텍스트는 REQ 문서가 제공한다(외부기억 원칙: 문서만 영속).
4. 스폰된 세션은 첫 행동으로 s9 last <REQ> 클레임 → 워처 중복 방지 + live 점멸 정합. 기존 방어장치(kill-switch·opt-in·쿨다운·시간당/일일 캡·note 인젝션 격리) 전부 유지.
5. 프롬프트 주입 경로는 '빠른 경로'로 유지 — 대화 중이면 워처보다 먼저 집는다. 워처는 침묵 시 보장.
