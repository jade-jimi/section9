```bash
### 1. 인스턴스 생성 (관리자, 1회) — gh가 있으니 --create면 사설 리포 생성까지 자동

### 2. 사용 시작 — 생성된 디렉토리에서
cd ~/example-work && bin/s9-install && bin/s9 code
### → 이후 평소처럼 프롬프트. 카드·문서·프로젝트가 전부 example-work 리포에 쌓입니다
```

명령이 해주는 것: 베이스 클론 → 리모트 구성(upstream=section9, origin=사설) → 데이터 track 전환(vault/users/projects/streams 커밋 대상, state는 sessions만 공유·chat 수신함 등은 로컬) → 초기 커밋 → 푸시. 원격 리포가 없어 푸시가 실패하면 생성 절차를 단계별로 안내합니다.

이유가 있습니다 — 실제로는 혼합 전략을 쓰고 있고, 구분 기준은 이렇습니다.

**위임한 것들**: Terminal 탭 재작업(2회), 채팅 패널 UI, 스트림 격리 백엔드, 가이드 챕터 — 이번 세션에서 워커 5회를 썼습니다. 공통점은 **파일이 분리되어 병렬이 성립**하고(워커가 web/index.html을 만지는 동안 저는 bin/s9), 자기완결적인 큰 덩어리라는 점입니다.

**리드가 직접 한 것들과 그 이유**:
1. **bin/s9 서버 작업** — 4천 줄 단일 파일을 여러 작업이 연속으로 건드렸습니다. 여기에 워커를 병렬로 붙이면 같은 파일에서 충돌합니다.
2. **사용자가 실시간으로 조종 중** — 오늘 몇 분 간격으로 중간 지시("그리고 이것도", "그건 빼고")가 들어왔습니다. 리드 직접 작업은 그 자리에서 방향을 틀 수 있지만, 스폰된 워커는 중간 수정을 흡수하는 비용이 큽니다. 실제로 Terminal 워커에 중간 지시를 3번 SendMessage로 릴레이해야 했습니다.
3. **위임 오버헤드가 작업보다 큰 S급 작업** — 워커는 대화 컨텍스트가 없어 긴 지시문을 써야 하고, 결과를 다시 검증해야 합니다. 오늘 워커 하나는 API 오류로 죽었고 하나는 테스트 플레이크로 39분을 썼습니다. 30분짜리 위임보다 5분짜리 직접 수정이 싼 경우가 많았습니다.
4. **되돌리기 어려운 작업** — 공개 리포 푸시, gh 인증, 라이브 서버 재시작은 전체 맥락과 권한 책임이 있는 리드가 직접 하는 게 맞다고 판단했습니다.

**워크플로를 안 쓴 이유**: 워크플로(다중 에이전트 오케스트레이션)는 명시적으로 요청하실 때만 쓰는 정책이고, 오늘 작업들은 "순차 + 대화형" 모양이라 팬아웃 구조와 맞지도 않았습니다. 다만 어울리는 일감은 분명 있습니다 — 예: 전체 코드베이스 감사, 대시보드 전 탭 크로스 검증, 문서 전수 정합성 검사 같은 넓게 펼치는 작업. 그런 걸 시키실 때 "워크플로로 해줘"라고 하시면 그렇게 진행합니다.

요약: 병렬 가능하고 자기완결적이면 위임, 단일 파일·대화형·소형·고위험이면 리드 직접 — 이 기준이 지금까지의 선택이었습니다. 특정 작업을 더 위임하길 원하시면 기준을 조정하겠습니다.
