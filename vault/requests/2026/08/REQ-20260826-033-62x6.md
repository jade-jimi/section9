## Original

대시보드 채팅 audit 경로(bin/s9 _chat_audit)는 분류가 request 가 아니면 `s9 log` 한 줄만 남기고 문서를 만들지 않는다. QST 생성(is_durable_question → s9 new question → bind last_qst)은 터미널 프롬프트 훅 s9-audit-prompt 에만 있다. 채팅으로 물은 질문은 전부 유실된다. 답 캡처(Stop 훅 last_qst)도 같이 이어져야 한다.

## Notes

### 2026-08-26T23:47:05+09:00 response (by sjpark1)

이 결함은 **입구가 둘인데 자가 하나뿐이었던 것**이다.

- 프롬프트 훅(터미널): 분류가 request 가 아니면 `is_durable_question` 을 한 번 더 보고, 남을 질문이면 QST 를 만든다.
- 대시보드 채팅: 분류가 request 가 아니면 **거기서 끝** — 질문이든 파편이든 `s9 log "chat: …"` 한 줄.

사용자는 주로 대시보드로 말한다. 그래서 화면의 질문은 영영 한 장이었다.

**고침**(`bin/s9`): 채팅 경로도 훅과 **같은 판정자**를 쓴다(`_chat_classifier` 옆에 `_chat_durable`). 판정 함수는 훅이 소유하고 채팅은 빌려 쓴다 — 입구마다 자를 따로 두면 같은 비대칭이 형태만 바꿔 되살아난다.

`_chat_question()` 이 하는 일은 셋뿐이다: QST 생성 → `bind last_qst` → 로그. 답은 붙이지 않는다. 그 세션이 이번 턴을 마칠 때 Stop 훅이 `last_qst` 를 보고 `answer` 노트로 자동 부착한다 — 터미널 경로와 **같은 이음매**다.

**반환값은 건드리지 않았다.** `chat_audit` 은 여전히 REQ id 또는 None 을 낸다. 그 값이 수신함 줄의 `req` 필드가 되고 받는 세션은 "그 id 로 상태를 관리하라"로 읽는다 — 질문 id 를 거기 실으면 상태 워크플로가 없는 문서에 전이를 걸게 된다.

**테스트** `tests/test_question_intake.py`: 019 워커가 이 결함을 `expectedFailure`(I1)로 명시해 두었다. 그대로 `unexpected success` 를 낸 뒤 데코레이터를 떼어 회귀 테스트로 굳혔다. I5 를 새로 붙였다 — 생성한 질문이 `last_qst` 로 묶이는가(이 이음매가 끊기면 질문은 남고 답은 채팅에만 남아 문서가 영원히 미답이 된다). I2·I3 이 경계: 채팅 request 는 그대로 REQ, 짧은 확인 발화는 여전히 무문서.

**주의**: 대시보드 서버가 옛 코드로 돌고 있으면 이 경로가 켜지지 않는다 — 채팅은 서버 프로세스가 처리하므로 `s9 serve --restart` 가 필요하다.
